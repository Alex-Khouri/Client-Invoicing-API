--- Further Development Opportunities ---

* More thorough validation for object property assignments
* More comprehensive use of type hints (e.g. function return types)
* Precautionary data validation checks within model classes (i.e. checking logically associated data fields)
* Impose restrictions for user passwords (e.g. mixed character types, minimum length)
* Implement timed expiry system for authentication session tokens
* Implement thread-locking mechanisms in all controllers to prevent race conditions with data processing
* Determine whether any other early returns within controllers should also raise warnings/errors (i.e. if those pathways indicate issues with back-end functionality)
* Use separate factories to generate model objects (rather than controllers)
* It would be more robust to implement unique ID management systems for all system entities (i.e. not just invoices), to avoid the problems that can arise with uniquely identifying entities by text names (e.g. duplicate entity names caused by text character restrictions)

--- Considerations for Productionisation ---

* Ensure that end-to-end encryption is implemented (for ensuring password and session token security during authentication)
* Ensure that user passwords are encrypted before being stored in persistent storage
* When integrating the API with the front-end application, it's helpful for the date values of invoice entries to reflect the timezone of the user (rather than that of the API). Therefore the front-end application should provide one of the following:
	- Current date
	- Timezone (which is subsequently used by the API to generate the date)
